1 INTRODUCTION

1.1 Purpose of the Project

The primary purpose of the AI-Based Driver Drowsiness Detection and Emergency Alert System is to reduce road accidents caused by driver fatigue. This specific Software Requirements Specification addresses the web application phase of the project, which operates entirely on-browser utilizing computer vision to detect early signs of sleepiness in real time.

1.2 Target Beneficiary

The system is targeted towards commercial fleet operators, long-distance truck drivers, and everyday commuters. By analyzing facial landmarks, it directly benefits the driver by preventing potential fatal accidents, while also indirectly benefiting other road users.

1.3 Project Scope

The scope of this web application includes a fully client-side implementation running within modern web browsers without requiring backend cloud infrastructure. It leverages a webcam feed to perform face tracking, extract eye regions via MediaPipe, and compute the Eye Aspect Ratio (EAR) and PERCLOS. A pre-trained custom Convolutional Neural Network (CNN) converted to TensorFlow.js acts as an active validation mechanism. When a drowsy state is detected, the system triggers stage 1 audio alarms. If unresolved, stage 2 initiates a simulated emergency SMS containing live GPS coordinates via browser geolocation APIs.

1.4 References

Implementation methodologies reference academic literature regarding EAR algorithms, TensorFlow model optimization literature (TensorFlow.js and TFLite specifications), and standard documentation for web geolocation and MediaPipe face mesh configurations.

2 PROJECT DESCRIPTION

2.1 Reference Algorithm

The core classification relies on a Hybrid detection method combining a CNN eye classifier, geometric Eye Aspect Ratio (EAR), and PERCLOS (Percentage of Eye Closure) calculations. The driver is marked as drowsy when the calculated EAR falls below a predefined threshold consistently or the PERCLOS metric exceeds the threshold. The CNN acts as a secondary verification using pre-cropped eye images fed into the TensorFlow.js model.

2.2 Characteristic of Data

The project utilizes the Driver Drowsiness Dataset (DDD) sourced from Kaggle. The dataset contains approximately 41,000 images categorized into two principal classes: Open Eye and Closed Eye. The characteristics of the data inherently include a wide array of variations designed to ensure model robustness. These variations feature different lighting conditions, an assortment of driver demographics, varying head poses, and the presence or absence of reflective eyewear (glasses and non-glasses drivers). The dataset is accessible via the following link: [https://share.google/GpacdsuOIEdxhh2N2].

Prior to training, images underwent strict data preprocessing using a custom Python pipeline. This included dataset cleaning, resizing images to a standard 112x112 pixel dimension, and normalizing pixel values by scaling them between 0 and 1 (pixel / 255). To mitigate overfitting, dataset augmentation techniques were applied extensively, including rotation, brightness variations, localized zoom, and horizontal flipping. The dataset was split into Training (80%), Validation (15%), and Testing (5%) subsets.

2.3 SWOT Analysis

Strengths: The system runs fully on-device natively in-browser, guaranteeing privacy and instantaneous latency. The dual-verification method (EAR + CNN) minimizes false positives.

Weaknesses: Webapp constraint depends strictly on browser camera capabilities, dropping performance slightly on older, low-clock-speed CPUs without WebGL acceleration.

Opportunities: Seamless transition into the final native Flutter Mobile App (End Sem product) utilizing INT8 quantized TFLite models.

Threats: Severe dynamic lighting changes (e.g., exiting a tunnel) can temporarily blind standard webcams.

2.4 Project Features

  • Real-time face detection pipeline built via Google MLKit (adapted for web via MediaPipe).
  • Eye tracking logic accurately pinpointing right and left ocular landmarks.
  • Instantaneous continuous calculations of EAR and PERCLOS values.
  • Two-stage Alert System (Audio alarm followed by simulated Emergency SMS).
  • GPS integration polling live coordinates during critical interventions.
  • Responsive User Interface overlay indicating metrics using TailwindCSS.

2.5 User Classes and Characteristics

Users require minimal technical proficiency. The interface requires only clicking a single "Start Monitoring" button and granting standard browser permissions for Camera and GPS capability. Administrators possess access to the underlying script debugging variables for threshold manipulation.

2.6 Design and Implementation Constraints

The overarching constraint is that the machine learning model must operate efficiently on-browser. The original Convolutional Neural Network (CNN) model format (model.h5) was transformed to run seamlessly offline. To achieve this, it relies on a standardized architecture. Training Details utilized an Adam Optimizer, a Sparse Categorical Crossentropy Loss Function, a Batch Size of 16, and matured over 17 Epochs using Early Stopping protocols. The model accomplished a Training Accuracy of ~99.97% and Testing Accuracy of ~99.86%.

2.8 Assumptions and Dependencies

It is assumed the user device contains an upward-facing or front-facing camera with at least 480p resolution. Dependencies include a modern web browser capable of rendering WebGL and executing synchronous JavaScript streams. The application relies entirely on JavaScript module CDNs for MediaPipe Face Mesh and TensorFlow.js operations.

3 SYSTEM REQUIREMENTS

3.1 User Interface

The Web Application interface uses HTML5, structured by vanilla CSS and TailwindCSS utilities, showcasing a dark-themed UI system ("glassmorphism"). It exhibits the live camera feed bounded by a facial landmark overlay. Real-time metrics presented encompass the EAR value, PERCLOS percentage, and the CNN prediction status. A distinct HUD overlay actively indicates driver alertness states ("AWAKE & ACTIVE", "DROWSY - WARNING", "CRITICAL ALERT").

3.2 Software Interface

Integration hinges on MediaPipe's Face Mesh APIs returning multi-face un-normalized landmark coordinates. TensorFlow.js is utilized for neural net verification. The location functionality queries the browser’s integrated navigator.geolocation API directly.

3.3 Database Interface

As an entirely stateless on-device web application, it maintains no persistent external database bindings in this current milestone. Metric histories are governed via short-lived volatile arrays persisting only for the lifecycle of the PERCLOS window memory.

3.4 Protocols

No external backend communication protocols (HTTP/REST) are leveraged, securing the pipeline dynamically over local streams. Local HTTPS certificates are nominally presumed during deployment for granting web-camera capabilities as standard browser policy dictates.

4 NON-FUNCTIONAL REQUIREMENTS

4.1 Performance Requirements

The system is strictly expected to compute frames at a minimum of 20 FPS (Frames Per Second) on moderately powered machines to guarantee that micro-sleep instances are accurately caught within the PERCLOS mathematical window limitations. Processing delays extending beyond 50 milliseconds per frame yield tracking desynchronization.

4.2 Security Requirements

Processing must be executed natively on-browser mitigating latency and protecting strict user privacy policies. Facial streams must not be compressed, transmitted, nor saved externally at any junction.

4.3 Software Quality Attributes

The application manifests high availability and fault tolerance. In instances where the visual input ceases or faces are untraceable, a "NO FACE DETECTED" safety net halts false positive aggregations instantly. Scalability translates effortlessly as a precursor to the upcoming natively coded Flutter iteration.

5 OTHER REQUIREMENTS

Hardware compatibility considerations ensure readiness for IoT transitions. While directly catering to widespread mobile clients in its future Android capacity, the underlying computational paradigms are curated to remain lightweight, ensuring they natively facilitate forthcoming Edge deployments, notably porting to a Raspberry Pi structure substituting typical speaker sets with physical buzzer circuitry.

Appendix A: Glossary

CNN: Convolutional Neural Network. A sequence of deep learning algorithms specialized for image recognition.

EAR: Eye Aspect Ratio. A quantifiable scaler value determining the physical openness of an eyelid utilizing specific distance vectors between facial landmarks.

PERCLOS: Percentage of Eye Closure over a rolling time window.

Appendix B: Analysis Model

The analysis predominantly surrounds a Confusion Matrix evaluated during model construction yielding values: [[1116, 2], [1, 972]], cementing an exceptionally low Type I and Type II error rate.

Appendix C: Issues List

Current development constraints occasionally witness slight EAR threshold inaccuracies dependent entirely on excessive glare traversing prescription eyeglasses. This edge case informs upcoming threshold calibrations.
